# Contributing to SEEING.md

`SEEING.md` should evolve from what happens when people use it, not from abstract claims about what it ought to do.

## Share a case

When reporting an experience, include what you can of the following:

1. What kind of work was being done?
2. What instruction activated `SEEING.md`?
3. What assumption, interpretation, or missing meaning did the system surface?
4. What question did it ask, if any?
5. Did the interruption materially change the result?
6. Where did the file add unnecessary friction?
7. What behavior should be preserved, removed, or changed?

Remove confidential information and identifying details before sharing.

## Propose a change

Explain the observed problem before proposing new language. Whenever possible, include a real case showing why the change matters. A useful revision should make consequential assumptions more visible without causing routine work to become hesitant or mechanical.

Changes should preserve the governing principle:

> Do not tell people what to see. Help make visible what may already be seeing for them.

## Versioning

- Wording and clarity changes normally produce a patch release.
- New or materially changed behaviors normally produce a minor release.
- Changes to the purpose or operating principles require a major release.

Each release should explain what changed and why.
